# 附件下载并发保护

问题证据：2026-10-27 正式应用仅有一个 worker，工单附件 ZIP 请求多次触发
`WORKER TIMEOUT`，同时普通页面和手机 session 请求出现取消。慢下载与其他
请求共享唯一同步 worker，会使页面排队。

本次调整：

- `gunicorn.conf.py` 使用 2 个进程，每进程 8 个线程；Docker 仍使用原启动命令，
  Gunicorn 从工作目录自动读取配置。数据库连接保存在 Flask 请求上下文 `g` 中。
- 工单 ZIP 每进程最多占用一个名额，覆盖生成和传输阶段。超出容量立即返回
  HTTP 503、`Retry-After: 10`，避免更多打包请求排队占满线程。
- ZIP 改为流式发送，每次读取 1 MiB，保留不压缩格式并使用 ZIP64 成员头。
  不生成完整临时 ZIP，不预读所有文件内容。慢速客户端会自然限制源文件读取，
  关闭 WSGI 迭代器时关闭当前源文件并释放下载名额。
  不预先提供 Content-Length；浏览器可能无法显示总进度百分比，不支持断点续传。
- 工作区等待从 15 秒调整为 45 秒，超时提示说明服务器繁忙或连接不稳定。
  手机端 session 错误提示不再笼统归咎于用户断网。

这属于容量保护和流式传输，并未把 ZIP 生成改成后台任务。最多两个工单下载可同时进行；
发送前仍需完成权限检查、文件列表扫描和结算 PDF 准备。ZIP 的文件目录元数据
仍随文件数量增长，但不随附件内容总大小增长。若需要恢复下载，应增加后台归档任务、
有权限校验的下载状态接口和过期清理；不能复用未经过权限校验的公共 ZIP 缓存。
其他类型的下载并未纳入这次工单 ZIP 限流。

验证：

```
.venv/Scripts/python.exe -m pytest --noconftest tests/test_download_capacity.py tests/test_streaming_zip.py -q
```

七项独立测试覆盖：生成期间普通页面可响应、慢下载期间拒绝额外归档、生成异常
释放名额、传输异常释放名额、实际工单 ZIP 内容及再次下载、分块读取/中途取消
停止源文件读取、ZIP64 格式/CRC 完整性/重名和缺失文件。
这些测试不连接数据库；`--noconftest` 绕过仓库全局的数据库重置钩子。
