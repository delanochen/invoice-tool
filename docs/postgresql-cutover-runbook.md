# PostgreSQL 切换与回退运行单（待演练批准）

本文件是操作顺序和放行条件，不是生产切换授权。当前生产仍使用 SQLite。
正式 main 已推进到 863acab。最新数据导入、业务对照、专项测试、并发及备份恢复已复验；手机浏览器保存和浏览器文件上传、保存前后图片预览均已通过。

默认 docker-compose.yml 仍使用 SQLite。PostgreSQL 配置必须显式启用并经过隔离验证，不能只改连接地址后假定已切换。

已新增可选 `deploy/docker-compose.postgresql.yml`，只有显式合并该覆盖文件时才启用 PostgreSQL。配置要求私有应用环境文件、所有者密码文件、已创建的数据卷及明确库名；未向外发布数据库端口。运行账号应为单独创建的非超级用户，不能把初始化所有者作为应用账号。2026-09-21 已完成隔离 Compose 部署演练：由基础配置与覆盖文件解析生成配置，保留数据库健康依赖、秘密文件和外部数据卷，替换为独立容器、内部网络及演练挂载，并去除正式隧道和照片后台服务。验证范围包含项目 Dockerfile 构建、默认应用启动命令、权限检查、应用及数据库容器重建后的数据完整性；不包含正式域名流量切换或正式后台任务启停。

`scripts/backup_postgresql.py` 可对明确指定的本机 PostgreSQL 容器生成新 `.dump`，文件权限 0600，拒绝覆盖已有文件，并检查归档目录可读。归档可读不代表恢复成功，仍必须执行独立恢复验证。脚本失败时可能留下不完整文件，不得作为有效备份使用；重新运行必须选择新文件名。

兼容分支的自动部署脚本已接入 `INVOICE_DATABASE_BACKEND=postgresql`：配置与运行后端不一致时停止，禁止自动切库；PostgreSQL 模式显式加载覆盖文件、调用专用备份工具，并在更新前后校验目标库、运行账号、权限和 schema 版本。SQLite 模式仍使用原部署与备份路径。6 项模拟测试和实际隔离库只读检查通过；尚未在正式服务器启用此分支改动。

正式切换前须暂停自动部署定时器，在最终迁移后使运行后端和显式配置一致，完成受控部署演练后再恢复自动更新。不能让旧自动部署脚本重建出未传入 DATABASE_URL 的应用实例。本运行单没有授权现在停止定时器或修改正式配置。

## 切换前必须具备的证据

- 固定正式代码提交、兼容分支提交和镜像摘要；后续正式代码变化需要重新评估。
- 最新一致性快照通过 integrity_check、foreign_key_check 和严格 schema 比对。
- 迁移后逐表行数与内容哈希、84 个外键及所有身份序列通过核验。数量必须以最新 schema 为准。
- 财务、薪资、结算、导出及附件内容与同一 SQLite 快照逐项对照；记录差异及处置结果。
- 最新代码的 SQLite 回归、PostgreSQL 集成、重复提交、桌面及手机操作验证通过。
- 备份在另一隔离库恢复成功；持续并发试验无错误、重复单据及金额差异。
- 核实后台任务、连接池、磁盘空间、权限、备份保留与告警；明确负责人和维护窗口。

原 scripts/migrate_postgresql.py 继续只允许 *_rehearsal 数据库。新的 scripts/migrate_postgresql_cutover.py 提供显式冻结快照入口，要求指定目标主机、库名、重复确认库名、源快照 SHA-256 和写入冻结声明。连接只允许 invoice_owner，拒绝 URL 查询参数覆盖目标；连接后再次核验数据库及账号，拒绝非空目标。已在隔离库 invoice_cutover_validation 验证成功导入及重复导入拒绝，不代表正式切换获得授权。

该入口的 --writes-frozen 仅记录操作者声明，无法证明外部写入进程已停止。正式操作必须先完成下述冻结步骤；隔离验证使用只读挂载的既有一致性副本及无人写入的新目标，没有冻结正式服务。--source 必须为绝对路径的独立 .sqlite3 快照，--result 必须为尚不存在的绝对路径文件。失败可能留下空结果文件，不能视为迁移成功；重试须使用新结果路径并先核实目标状态。

## 维护窗口执行顺序

1. 取得正式切换授权，记录开始时间、代码版本、负责人及回退判断时间。
2. 暂停所有写入入口：Web/API、照片处理、定时任务及其他写库进程；提示移动端暂停上传。确认在途请求完成，队列与重试任务不会继续写入。
3. 在写入冻结期间创建 SQLite 一致性备份，并同步附件、照片文件与校验清单。保留数据库、文件、配置和代码的配套版本，避免直接复制运行中的主库而遗漏 WAL。
4. 在非公开网络准备空 PostgreSQL 正式目标，迁移角色与运行角色分离；使用审查后的迁移入口。运行角色不得创建 schema 或改写迁移元数据。
5. 迁移完成但仍保持业务写入冻结。核验表内容、外键、序列、业务金额和附件清单；任何不一致均停止放行。
6. 在受控入口使用目标配置验证登录、关键查询、导出及预览。记录如需进行的合成写入及清理结果；禁止实际邮件或第三方业务操作。
7. 全部条件通过后才将正式应用指向 PostgreSQL，按顺序恢复写入和后台任务。核实只有一个正式写入数据源，禁止双写或旧进程继续写 SQLite。
8. 观察错误率、数据库锁等待、连接数、响应时间、照片队列和关键业务金额；留存验收记录及首份 PostgreSQL 备份。

演练中的亚秒级导入时间不等于维护窗口长度。须在最新完整数据和文件上计时，把冻结、备份、核验、启动和观察时间全部纳入。

## 回退边界

**放行业务写入前：** 停止目标应用和任务，恢复原 SQLite 配置、匹配的代码和文件集合；确认没有遗留 PostgreSQL 写入进程，再恢复业务。记录失败阶段并保留隔离目标用于分析。

**PostgreSQL 已接收新业务写入后：** 不得直接改回旧 SQLite。先重新冻结全部写入，备份 PostgreSQL 和新增附件，核对切换后的新增、修改、删除记录与审计轨迹。优先修复继续运行；确需回退时，必须制定并验证增量回灌和附件对账方案，明确确认不会丢失已接受的业务数据后才执行。

目前没有经过验证的 PostgreSQL → SQLite 自动增量回退工具，因此“随时改回连接地址”不是可用回退方案。
